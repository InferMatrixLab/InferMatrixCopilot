## Plan at a glance

Keep the two packages. Copilot owns shared execution, review computation and
knowledge capabilities; ReviewBot owns scheduling, routing decisions, GitHub
business state and publication. Give each capability one implementation and
migrate every caller before deleting its superseded implementation.

The knowledge quality reviews in different init steps are **not identical**.
Share their execution and recovery machinery, while preserving the seven
explicit stage policies in the matrix below. A common provider or JSON decoder
alone does not consolidate their correction, accounting and checkpoint loops.

Deliver the work in six reviewable phases:

1. Freeze contracts, persisted fixtures, stage policies and the complete
   owner/caller/deletion inventory.
2. Consolidate neutral types, knowledge constraints, evidence codecs, Git
   snapshots, diff parsing and review/publication predicates.
3. Consolidate provider execution, process supervision, credential policies,
   Direct/Strict host communication and application composition. Include probes,
   rebase, improvement and vendor SDK subprocesses in the caller audit.
4. Consolidate curation and all init/maintenance quality-review mechanisms;
   preserve acceptance differences, rendering contracts and durable recovery.
5. Complete durable Direct/Strict execution through the public SDK in both local
   and remote deployments, including legacy identities and stale-head refusal.
6. Verify deletion and dependency boundaries, test the installed paired wheels,
   run the frozen quality comparison, and prepare immutable releases with
   in-flight retention and rollback evidence.

Each phase must identify its migrated callers, deleted bodies, retained policy
differences and validation evidence. Track implementation, deterministic tests,
model-quality comparison and rollout separately. The sections below define the
interfaces, individual gap fixes and exit criteria for these phases.

  delivery. Restricted structured completion and provider descriptors are public

  Recovery retains execution location, release, profile and original key. A lost

  snapshot results while retaining distinct tree, wiki, lifecycle and semantic

  their hosts. Keep budget authorization and journals with their domains while

## Boundaries that remain

- Copilot owns provider execution, review computation, knowledge workflows and
  domain validation. ReviewBot uses its public SDK only.
- ReviewBot owns scheduling, routing decisions, GitHub evidence acquisition,
  business retries, publication and receipts. The SDK-host subprocess client is
  a ReviewBot integration capability; consolidating it does not move GitHub
  business policy into Copilot.
- Application composition supplies workflow policies. The execution kernel must
  not import knowledge or review business logic.
- Bot jobs, Copilot runs, knowledge state and domain budget journals retain
  separate authority. Unknown execution outcomes remain pending reconciliation.
- Different quality rubrics, append-only/lifecycle renderers, and provider I/O
  formats remain explicit strategies. They must not carry independent copies of
  the common lifecycle, validation or recovery mechanisms.

No new user configuration or CLI behavior is intended. Preserve existing APIs,
commands, state formats and stage acceptance policies. Preserve the already
agreed refusal to publish on head drift.

## Slice 2 — one provider process supervisor

Separate process ownership from output transport. The supervisor owns launch,
process groups, bounded stdin, cancellation, idle/absolute deadlines, termination
grace, descendant cleanup and final outcome collection. Pipe streaming, buffered
capture and ZCode file spooling are I/O strategies. Preserve ZCode's anonymous
file spooling: replacing it with pipes would risk reintroducing output loss.

Return one internal process outcome with exit status, timeout/cancellation reason,
partial output and diagnostics. Existing wrappers translate this into compatible
return shapes. Provider adapters keep event decoding, model identity, resume
arguments and capability checks. Unsupported policies fail before dispatch.

Include authentication and readiness probes in the caller inventory. Public
readiness, subscription checks and native adapter probes must use the same
supervisor and explicitly composed credential policy; they must not retain
independent subprocess invocation bodies. Preserve provider-specific probe
arguments and interpretation as adapter policy.

Migrate buffered execution, streaming execution and ZCode in that order, deleting
each superseded lifecycle body. Distinguish agent process trees, which are owned
by the supervisor, from durable workers that intentionally outlive an SDK host.

Validate success, failed launch, malformed/partial output, blocked stdin, full
stderr, idle and absolute timeout, explicit cancellation, descendant cleanup and
ZCode spool completion with fake executables. Cover supported platform-specific
termination behavior. Check accounting settlement once per call, explicit unknown
usage and actual overspend; quota policy remains domain-owned.

## Slice 3 — one Direct/Strict host client

Extract a ReviewBot client for the existing JSON-lines host protocol. Own process
creation, serialized exchanges, bounded reads/writes, decoding, close and cleanup
there. Direct and Strict supply configuration, capability requirements and typed
error translation. Keep existing protocol shapes unless an additive versioned
change is necessary.

Use bounded roundtrips for both modes. A timeout, malformed reply or lost reply
after dispatch is uncertain, not evidence of failure. Dispose of the failed
transport and reconcile the original reservation/run using the same business
key, execution location, release and profile. Do not blindly replay a mutating
operation or trigger provider fallback. Reconnecting performs capability checks
again. Closing a host must not kill its independently durable workers.

Validate Direct/Strict conformance for normal replies, blocked write/read, EOF,
invalid JSON, host restart, close timeout and capability mismatch. Inject crashes
before and after reservation/start responses and run-ID persistence; assert one
paid execution and recovery of the original identity. Remove both old exchange
implementations once their callers use the client.

## Integration and release gates

The recommended order is 0 → 1 → 2 → 3 → 4 → 5 → 6. Host communication has no
hard dependency on diff or knowledge work and should ship early once its recovery
tests pass. Each slice must migrate callers and delete old bodies together.

1. Strengthen dependency guards: bot public-SDK-only imports; no bot vendor CLI
   logic; no domain-to-SDK/transport imports; no kernel-to-domain imports. Add
   focused guards against the specific superseded entry points returning.
2. Update the ownership inventory with actual implementations and remaining
   exceptions. Audit model-call accounting and trace hooks across all migrated
   entry points; record any additional duplication rather than declaring closure
   from helper reuse or symbol counts alone.
3. Run affected suites per slice, then full paired suites and installed-wheel
   tests without source-path injection. Test packaged validators, legacy SDK
   exports/state, local/remote Direct/Strict and subprocess import provenance.
4. Report production-line and AST changes against both the original baseline and
   the pre-completion refactor snapshot. Reduction is informative, not a gate.
5. Prepare a frozen shadow set covering every init policy and review mode. Compare
   acceptance/rejection, actionable findings, correction frequency, cost, latency
   and uncertain outcomes. Define tolerances before running; use a bounded budget
   and no publication. Deterministic tests alone cannot establish model quality.
   Include maintenance audit as a separate quality policy. Freeze inputs, labels,
   backend/profile, artifact identities and acceptance tolerances before dispatch.
   Enforce the ceiling on actual native model calls, including internal review
   calls and repairs, rather than counting an entire workflow as one call. Keep
   raw responses, validation results and unresolved outcomes separately; a lost
   response cannot be bypassed by assigning a new evaluation call ID.
6. Publish immutable paired artifacts and negotiate required capabilities before

## Risks and decisions to preserve

- Over-generalizing quality review can change accepted knowledge. Share execution
  and recovery while keeping versioned rubrics, evidence scopes and acceptance
  policies explicit; evaluate each init path separately.
- A lost response is not a failed execution. Persist dispatch intent before the
  call, bind recovery to the original identity, and retain unresolved outcomes
  until reconciliation establishes what happened.
- Passing source tests can hide missing packaged resources or private imports.
  Validate the actual paired wheels and public SDK from an isolated environment.
- Large moves can leave duplicate implementations behind compatible wrappers.
  Require a function-level ledger with owner, every caller, removed body,
  intentional policy differences and verification evidence before closing a
  capability. Line and AST counts are supporting measurements only.
- Rolling back new admissions does not roll back existing paid executions.
  Retain the original worker environment and state until outstanding runs and
  publication receipts settle.
